# Norocel 2 — техническое задание для агента

**Дата:** 2 октября 2026 года  
**Результат:** React + TypeScript, mobile-first responsive PWA; Laravel API; собственная SQL-база на хостинге.  
**Основной источник:** NOROCEL_AUDIT.md от 02.10.2026, статический аудит master / 25d3a31.

## 1. Задача и границы

Перенести функциональность и пользовательские данные Norocel на новую архитектуру. Сохранить финансовый смысл доходов, расходов, переводов, обменов, накоплений и погашения обязательств. Исправить нарушения целостности и сделать основные сценарии доступными с телефона и компьютера.

Это задание описывает целевое поведение. Старые файлы JavaScript и SQL-триггеры — источник для проверки миграции, а не обязательный способ реализации.

Аудит выполнен по коду: он не доказывает состояние рабочей базы и не заменяет проверку приложения под авторизацией. До миграции агент проверяет фактическую схему и данные доступным ему способом, фиксирует расхождения с аудитом. Нельзя объявлять непроверенные сценарии протестированными.

Работать в отдельной ветке. Старый рабочий вариант сохранять до готовности замены. Разработка, тесты, адаптеры миграции и репетиция переноса выполняются на локальной или отдельной тестовой базе. Переключение рабочего приложения и разрушительные действия над рабочими данными — отдельная операция после проверки результата владельцем.

## 2. Техническая архитектура

### 2.1. Стек

| Слой | Решение |
|---|---|
| Frontend | React, TypeScript strict, Vite, React Router |
| Серверное состояние UI | TanStack Query или эквивалентный query cache с явной инвалидацией |
| Backend | Laravel, JSON API /api/v1, Form Requests, Policies, сервисы/команды предметной области |
| База | MySQL с InnoDB на существующем хостинге; если хостинг уже предоставляет PostgreSQL и он выбран до старта — PostgreSQL |
| Web auth | Sanctum, сессионные cookies и CSRF |
| Сессии и начальный кэш | Доступный на хостинге стандартный драйвер Laravel; Redis не является обязательной зависимостью |
| Сборка | В CI/локально; на PHP-хостинг загружаются готовые frontend assets и Laravel |
| PWA | Manifest, иконки, service worker с явно ограниченной политикой кэширования |

Выбрать одну production СУБД перед созданием миграций. Не поддерживать две базы ценой упрощения транзакционных проверок. SQLite допустим для вспомогательных задач, но не заменяет выбранную СУБД в проверке блокировок.

Зафиксировать версии PHP, Laravel, Node и пакетов после проверки среды хостинга; использовать поддерживаемые совместимые версии и lockfiles. Документация Laravel 13.x приведена в источниках как ориентир, а не как разрешение обновить несовместимый хостинг.

### 2.2. Размещение

Предпочтительно один origin: React по основному адресу, Laravel API по /api/v1, auth endpoints по /auth и /sanctum. Роутинг веб-сервера должен отдавать SPA для пользовательских путей и JSON/ошибки Laravel для API, а не index.html вместо API-ответа.

Node runtime в production не нужен. Document root Laravel — public. .env, код приложения, резервные копии и импортированные файлы не должны быть доступны через веб.

React не обращается к Supabase после перехода. Supabase допускается только в отдельном серверном адаптере миграции. Секретный ключ такого адаптера не попадает во frontend, логи или экспорт пользователя.

### 2.3. Разделение ответственности

- Laravel хранит данные, проверяет владение и бизнес-правила, считает балансы и отчёты.
- React отображает серверные значения и выполняет предварительную проверку форм.
- Локальные расчёты React используются для preview; ответ сервера является окончательным.
- UI не выполняет финансовый сценарий несколькими независимыми CRUD-запросами.
- Один backend command выполняет весь перевод, целевой расход, погашение или импорт в одной DB-транзакции.

Нужные команды: CreateIncome, CreateExpense, TransferMoney, ExchangeMoney, AmendOperation, VoidOperation, SpendForGoal, SettleLiability, VoidLiabilitySettlement, ImportWorkspace.

## 3. Общие правила денег, дат и доступа

### 3.1. Деньги

В этапе A поддержать MDL, EUR, USD. В этапе B добавить RON. Реестр валют содержит код и количество десятичных разрядов; у перечисленных валют — 2.

- Денежные значения в базе — целые минимальные единицы, BIGINT. 100.25 MDL хранится как 10025.
- В JSON все money fields передавать строками: "10025", включая отрицательные delta и вычисленные остатки.
- Во frontend использовать BigInt/точную decimal-библиотеку; не выполнять финансовую арифметику через Number.
- На backend не использовать float для денег и курсов. Деление и умножение курсов — точная decimal-арифметика.
- Ручной ввод с большим числом десятичных знаков, чем разрешено валютой, отклонять, а не молча округлять.
- Конверсию по курсу округлять один раз до минимальной единицы получателя, ROUND_HALF_UP. Промежуточные расчёты сохраняют точность.
- Верхний предел каждой money field и каждого остатка: 999999999999999 минимальных единиц. Проверять переполнение при суммировании.
- Агрегаты отчётов могут превышать предел одной записи: суммировать их точной decimal/BigInt-арифметикой и отдавать строками, не приводить SUM к ограниченному PHP int. Для геометрии графика допустим числовой масштаб, но подписи/tooltip берутся из точных значений.
- operation.amount_minor и target_amount_minor положительны; opening_balance_minor >= 0.

В API не смешивать отображаемые суммы и минимальные единицы. Для формы отдельные функции parseMoney / formatMoney с учётом локали; пробелы группировки и десятичная запятая не отправляются на сервер.

### 3.2. Даты

- occurred_on, due_on, deadline — DATE в формате YYYY-MM-DD.
- period_month — первое число месяца, YYYY-MM-01.
- created_at, updated_at и технические времена — UTC.
- timezone профиля определяет «сегодня» и месяц по умолчанию; для миграции без timezone — Europe/Chisinau.
- Дата операции не сдвигается при смене timezone или переводе браузера в другой часовой пояс.
- Операция является проведённой сразу после сохранения. Как в исходной модели, текущий остаток включает все posted-операции, независимо от occurred_on. Если выбрана будущая дата, форма явно сообщает, что сумма повлияет на остаток сразу.
- Планируемые платежи — отдельный будущий сценарий. Не смешивать их с posted-операциями.

### 3.3. Владелец и роль администратора

Все финансовые сущности принадлежат одному user. user_id определяется авторизованной сессией и не принимается как произвольное поле публичного API.

Каждая переданная ссылка проверяется на принадлежность тому же user: оба счёта перевода, категория, цель, обязательство, бюджет. Проверка нужна и при UPDATE, и при импорте. По возможности добавить составные FK (user_id, linked_id) к уникальному (user_id, id); это усиливает целостность, но не заменяет Policies.

Admin вправе управлять разрешёнными полями пользователей. Эта роль не даёт доступ к accounts, operations, goals, budgets, liabilities, отчётам и backup чужого пользователя. Не использовать глобальное разрешение всех Policies для admin.

## 4. Модель данных

Все идентификаторы предметной области — UUID. Сохранять старые UUID при переносе, если нет конфликтов; при замене workspace использовать явную таблицу remapping. Добавить timestamps, FK и индексы по user_id и ключам выборок.

### 4.1. users и user_settings

users:

- id, email, password hash, email_verified_at;
- full_name, avatar_url nullable;
- billing_plan: regular | premium;
- is_admin, last_seen_at;
- timestamps.

user_settings:

- user_id, locale: ro | ru | en;
- base_currency_code;
- theme: light | dark | system;
- timezone;
- workspace_revision — версия пользовательских данных для импорта и согласованных снимков.
- workspace_generation — поколение данных; увеличивается при полном restore.

email в users — единственный подтверждённый email. Смена email идёт через отдельный подтверждаемый сценарий. billing_plan / is_admin не входят в обычный self-update и пользовательский restore.

### 4.2. accounts

- id, user_id, name;
- kind: regular | savings;
- currency_code;
- opening_balance_minor;
- include_in_total boolean;
- archived_at nullable;
- timestamps, revision.

current_balance не хранить как независимый редактируемый столбец. Считать из opening balance и posted-операций.

Валюта и opening balance фиксируются при создании; их нельзя менять обычным PATCH. Переименование и include_in_total разрешены. kind можно изменить, если счёт не связан с целью; изменение типа не меняет историю и деньги.

Архив запрещает новые операции по счёту, но не обнуляет остаток и не исключает его автоматически из общей суммы. Разархивирование доступно. Счёт с историей не удалять; пустой счёт с нулевым opening balance и без связей можно удалить.

### 4.3. categories

- id, user_id;
- kind: income | expense;
- system_code nullable, name nullable;
- is_system, archived_at;
- timestamps.

Системные категории создавать как реальные строки каждого user при инициализации. Подписи переводятся по system_code; собственное имя пользовательской категории — пользовательский текст.

Системные коды из старого проекта:

| Тип | Коды |
|---|---|
| Доход | salary, freelance, investments, gifts, other_income |
| Расход | food, transport, housing, entertainment, shopping, health, education, utilities, other_expense |
| Целевой расход | goal_expense |

Для пользовательских имён сохранить уникальность без учёта регистра внутри user + kind. Используемую категорию архивировать; не оставлять операции и бюджеты с текстовой ссылкой. Тип категории после использования неизменяем.

Служебную goal_expense нельзя переименовать, архивировать или создать как пользовательскую категорию. Архивирование обычной категории сохраняет текущие/исторические budgets, но останавливает её шаблоны с будущего месяца; новые лимиты по архивной категории не создаются.

### 4.4. operations

Одна строка представляет одну пользовательскую операцию.

| Поле | Смысл |
|---|---|
| id, user_id | Идентификатор и владелец |
| type | income / expense / transfer / exchange |
| status | posted / voided |
| occurred_on, description | Дата учёта и комментарий |
| account_id | Счёт income/expense |
| from_account_id, to_account_id | Два счёта transfer/exchange |
| amount_minor, currency_code | Сумма income/expense либо списанная сумма перевода |
| target_amount_minor, target_currency_code | Полученная сумма и валюта перевода |
| quoted_rate nullable | Введённый пользователем курс при расчёте |
| effective_rate nullable | amount / target_amount, в основных единицах валют |
| category_id nullable | FK для income/expense |
| goal_id nullable | FK только для целевого expense |
| goal_completion_requested | Явная отметка «завершить цель» в целевом расходе |
| revision | Версия для защиты от изменения устаревшей формы |
| voided_at nullable | Когда операция отменена |
| legacy_metadata nullable | Исходный тип/курс/ключ категории и замечания адаптера миграции; не источник денег |
| timestamps | Техническое время |

quoted_rate/effective_rate — DECIMAL(30,12) или эквивалентная точная модель. Курс отдаётся JSON-строкой.

Если положительный курс невозможно представить в выбранной точности или он округляется до нуля, отклонить ввод с FX_RATE_OUT_OF_RANGE. Не сохранять нулевой effective_rate для ненулевых сумм.

DB CHECK / сервисная валидация формы:

- income/expense: account_id задан; from/to/target fields и FX fields отсутствуют; category_id обязателен;
- transfer/exchange: account_id/category_id/goal_id отсутствуют; from/to различны; обе суммы и валюты заданы;
- transfer: валюты одинаковы, суммы равны, effective_rate = 1;
- exchange: валюты различаются; effective_rate соответствует фактическим суммам;
- goal_id и goal_completion_requested разрешены только для expense с категорией goal_expense.

Системную категорию goal_expense назначает серверная команда. Обычная форма расхода не создаёт незавершённую связь с целью.

### 4.5. operation_revisions

id, user_id, operation_id, actor_id, action, before_payload, after_payload, created_at.

Хранить изменения и отмены операции для диагностики и отображения истории. Это журнал изменений, не источник балансов. Финансовая отмена меняет status на voided; отдельную зеркальную income/expense не создавать.

### 4.6. goals

- id, user_id, name, icon nullable;
- target_amount_minor, currency_code, deadline nullable;
- savings_account_id: unique, nullable только для legacy-целей;
- cancelled_at nullable;
- legacy_saved_minor nullable, legacy_status nullable, legacy_completed_at nullable — только для явно помеченных старых непривязанных/несогласованных целей;
- timestamps, revision.

Новая цель всегда связана с одним savings-счётом той же валюты. Один счёт — максимум одна цель. Прогресс и status возвращаются как вычисленная проекция, не как независимо редактируемые поля.

### 4.7. budgets и budget_templates

budgets:

- id, user_id, category_id expense;
- period_month, currency_code, limit_minor;
- disabled boolean — явная отмена лимита этого месяца, которую не восстанавливает шаблон;
- source_template_id nullable;
- timestamps, revision;
- unique(user_id, category_id, period_month).

budget_templates:

- id, user_id, category_id expense, currency_code, limit_minor;
- start_month, stop_month nullable;
- timestamps, revision.

Шаблон создаёт лимит для следующих месяцев. Для уже созданного monthly budget лимит и валюта фиксированы; изменение шаблона их не переписывает. Не допускать перекрывающихся активных шаблонов одной категории.

EnsureMonthlyBudgets идемпотентно материализует недостающие monthly rows для месяца из действующих шаблонов. Запускается при открытии раздела бюджетов через явный backend command, либо планировщиком; обычный GET не должен скрыто менять workspace. Вручную заданный бюджет имеет приоритет.

### 4.8. liabilities и liability_settlements

liabilities:

- id, user_id, kind: receivable | payable | credit;
- counterparty_name, principal_minor, currency_code;
- due_on nullable, comment nullable;
- cancelled_at nullable;
- timestamps, revision.

liability_settlements:

- id, user_id, liability_id UNIQUE, operation_id UNIQUE;
- timestamps.

Этап A: полное погашение одним доходом/расходом, частичных платежей нет. Сумма и дата погашения берутся из связанной операции. Состояние settled выводится из существования валидной settlement-связи, open — из её отсутствия, cancelled — из cancelled_at.

### 4.9. Служебные таблицы

- command_deduplication: user_id, workspace_generation, command_key, request_hash, response/result reference, created_at; unique(user_id, command_key).

Служебные сведения не входят в обычную финансовую модель. Привилегированные поля не восстанавливаются из файла пользователя.

## 5. Финансовые правила и команды

### 5.1. Остаток счёта

Для каждого счёта и только posted-операций:

~~~text
balance =
  opening_balance
  + SUM(income.amount)
  - SUM(expense.amount)
  - SUM(outgoing transfer/exchange.amount)
  + SUM(incoming transfer/exchange.target_amount)
~~~

Остаток всегда выражен в валюте этого счёта. Начальный остаток не считается доходом. Перевод и обмен не считаются доходом/расходом в отчёте денежного потока.

Обычные новые данные должны удовлетворять balance >= 0 после каждой команды. Проверять результат для всех затронутых счетов после создания, изменения и отмены операции, включая счёт-получатель перевода. Если команда нарушает правило, целиком отклонить её с понятным сообщением.

Это проверка текущего итогового остатка. Запрет отрицательного остатка на каждом историческом дне не вводится: задним числом можно уточнять дату записи, сохраняя правильный итог. Исторический график может показать отрицательный промежуточный остаток; он не должен скрываться или заменяться нулём.

Если legacy-данные уже имеют отрицательный текущий остаток, dry run сообщает о них отдельно. Импорт не создаёт скрытую «компенсацию». Такой workspace требует отдельного решения владельца; до него перенос не применяется.

| Действие | Влияние на деньги | Связи и состояние |

| Доход | +amount на account | Одна operation |
| Расход | −amount на account | Одна operation |

### 5.3. Доход и расход

Выбор account, сумма, category, occurred_on, description. Валюта берётся из account; её нельзя произвольно подменить в payload.

Категория должна совпадать с type, принадлежать user и быть активной для новой записи. Редактирование старой записи может сохранять уже архивированную категорию, но выбирать новую архивированную нельзя.

Архивированный account не принимает новые операции и изменение сумм/направления существующих. Сначала требуется разархивировать его. Просмотр, изменение комментария и отмена старой операции доступны с общей проверкой балансов.

### 5.4. Перевод в одной валюте

Пример: MAIB MDL → Наличные MDL, 1000 MDL.

- Source и target — разные счета одного user.
- Оба счёта активны, валюты одинаковы.
- type=transfer; суммы равны, effective_rate=1.
- Для обоих счетов это одна логическая операция с одним ID.
- В общем журнале одна строка; в истории каждого счёта — соответствующая delta.
- Не создавать отдельные income/expense, иначе аналитика будет завышена.

### 5.5. Обмен валют

Пример: MAIB MDL → Savings USD, списано 1800 MDL, получено 100 USD.

~~~text
source amount = 1800 MDL
target amount = 100 USD
effective rate = 18 MDL за 1 USD
~~~

Конвенция курса сохраняется из старой модели: единиц исходной валюты за одну единицу целевой.

Два режима формы:

1. «Списано + получено»: вводятся обе суммы; сервер вычисляет effective_rate.
2. «Списано + курс»: вводятся сумма и quoted_rate; target рассчитывается как round(source / quoted_rate) в валюте получателя.

Если клиент прислал quoted_rate и обе суммы, сервер проверяет target по той же формуле и правилам округления. Противоречивый ввод отклоняется. Различие quoted и effective курса из-за округления до центов допустимо и показывается в деталях.

При делении минимальные единицы сначала приводятся к основным единицам с учётом scale валют. Нулевой курс или target, округлившийся до нуля, запрещены.

type определяется сервером по валютам счетов. Нельзя отправить transfer между разными валютами или exchange между одинаковыми.

Детали показывают оба счёта, обе суммы, quoted/effective rate, дату и комментарий. Справочный курс из этапа B может только заполнить preview. После сохранения фактические суммы и курс обмена не изменяются при обновлении справочных курсов.

Комиссия не выделяется отдельным типом в этапе A. Если пользователь хочет учесть отдельную комиссию, он создаёт отдельный expense; спрятанную комиссию нельзя автоматически вычитать второй раз.

### 5.6. Редактирование и отмена

Разрешить редактировать все четыре типа операций из общего журнала. Менять тип между income/expense и transfer/exchange обычным PATCH нельзя: отменить и создать новую. Между transfer/exchange тип может измениться при выборе других счетов и валют, с полной проверкой новой формы.

Алгоритм редактирования:

1. Проверить revision операции и все связи.
2. Рассчитать остатки затронутых старых и новых счетов без старого эффекта.
3. Применить новый эффект.
4. Проверить неотрицательность и верхний предел каждого результата.
5. Записать изменения, revision и before/after в одной DB-транзакции.
6. Пересчитать зависимые проекции цели и обязательства.

Отмена выполняется backend-командой, устанавливает voided и исключает эффект сразу из всех счетов и отчётов. Операция остаётся доступной по фильтру «Отменённые». Повторная отмена не должна изменить баланс ещё раз.

Контрольные примеры:

- +1000 доход, −900 расход → остаток 100. Отмена дохода отклоняется: результат −900.
- A=1000, B=0; перевод 500 на B; расход 450 с B. Отмена перевода отклоняется: B стал бы −450.
- Редактирование полученной суммы обмена проверяет получателя, даже если на source достаточно денег.
- Перевод, удалённый из истории одного счёта, отменяется полностью, а не только для этой стороны.

Связанные операции имеют отдельные сценарии:

- goal expense редактируется через форму целевого расхода; нельзя произвольно снять goal_id или перенести его на чужой/неподходящий счёт;
- settlement operation редактируется/отменяется через сценарий обязательства; обычный PATCH финансовых полей такой операции отклоняется;
- отмена settlement одновременно удаляет действующую settlement-связь и возвращает обязательство в open;
- запрет отмены из-за отрицательного остатка возвращает ошибку без каких-либо изменений связи.

### 5.7. Цели и «отложено»

«Отложено» — деньги на savings accounts. Это не дополнительная сумма поверх баланса этих же счетов. Цель показывает назначение конкретного savings account и не создаёт второй денежный остаток.

Новая цель содержит target, currency, optional deadline/icon, существующий подходящий savings account или создаёт новый savings account в той же команде.

Сохранить формулу исходного проекта:

~~~text
saved_now      = balance(linked savings account)
spent_on_goal  = SUM(posted goal expenses)
funded_lifetime = saved_now + spent_on_goal
progress       = MIN(100%, funded_lifetime / target)
~~~

Показывать отдельно «На счёте сейчас», «Потрачено на цель», «Всего направлено на цель» и процент. Это объясняет, почему после целевого расхода прогресс не падает.

Перевод денег со связанного счёта на другой счёт и нецелевой расход уменьшают funded_lifetime. Целевой расход уменьшает saved_now и увеличивает spent_on_goal на ту же сумму. Связанный счёт имеет валюту цели; exchange при пополнении зачисляет сумму в эту валюту.

Status вычисляется:

| Условие, в порядке приоритета | Status / подпись |
|---|---|
| cancelled_at задан | cancelled / «Отменена» |
| Есть действующий goal expense с goal_completion_requested или spent_on_goal >= target | spent / «Завершена» |
| funded_lifetime >= target | reached / «Сумма собрана» |
| Иначе | active / «Накопление» |

legacy_status=spent участвует только в совместимой проекции импортированных целей и явно отмечается как перенесённое состояние. Дату завершения показывать лишь если она присутствует в исходных данных; не придумывать её.

«Пополнить» открывает перевод/обмен на связанный счёт; не создаёт доход из ниоткуда.

«Потратить на цель» создаёт expense с нужного savings account и goal_id. Checkbox «Завершить цель» — явное решение пользователя даже при меньшей сумме; сохранить его в goal_completion_requested конкретной операции. Операция и её completion marker сохраняются атомарно.

При отмене/редактировании такого расхода status и прогресс пересчитываются по оставшимся posted-операциям; старая отметка completed не остаётся сама по себе. completed_at в API — вычисленная дата первой действующей операции, выполнившей условие завершения в порядке occurred_on, created_at, id.

Отмена/возобновление цели не перемещает деньги. Для cancelled цели нельзя создавать новый целевой расход, но её счёт остаётся доступным для обычных разрешённых операций.

Нельзя отвязать счёт или изменить валюту цели с историей расходов. Смена target/deadline/name разрешена и пересчитывает проекцию. Goal с историей не удалять физически. Использованный savings account нельзя привязать к другой новой цели с потерей старого назначения.

### 5.8. Обязательства и кредиты

Долг — запись обязательства, не автоматическое движение денег. При создании форма объясняет: уже состоявшуюся выдачу/получение денег пользователь записывает отдельной операцией, если её ещё нет. Не создавать повторный expense/income при миграции.

На карточке: направление, контрагент, principal, currency, due date, comment, status. Итоги отдельно по валютам и по трём типам.

Полное погашение:

- receivable → income в сумме principal;
- payable / credit → expense в сумме principal;
- выбранный account имеет ту же currency;
- категория соответствующего типа выбирается в форме; сумма фиксирована и не редактируется;
- операция и settlement создаются одной DB-транзакцией;
- повторное погашение уже settled обязательства не создаёт вторую операцию.

Principal, currency и kind нельзя менять после погашения. Имя, комментарий и срок можно уточнить. Для исправления суммы сначала отменить погашение, затем изменить открытое обязательство и погасить заново.

После отмены погашения денежный эффект исключается, обязательство возвращается в open. Отдельная отмена открытого обязательства не меняет баланс. Settled обязательство не удалять/отменять так, чтобы операция осталась без объяснимой связи.

В этапе A погашения входят в общий cash flow, как в текущем приложении; журнал и отчёты показывают признак «погашение долга», чтобы возврат долга не выглядел зарплатой. Анализ доходности и исключение погашений — отдельный фильтр, а не скрытая смена суммы.

### 5.9. Бюджеты

Один бюджет категории на месяц, с конкретной currency и limit. Категория только expense. Факт учитывает posted expenses нужной категории в периоде; transfer/exchange и opening balance не участвуют.

Этап A: в fact входят операции в валюте бюджета. Расходы этой категории в других валютах показываются рядом отдельными суммами и сообщением «не включены в этот лимит». Нельзя скрывать их или выдавать сумму одной валюты за все расходы.

Этап B: эти расходы конвертируются в валюту бюджета по историческим reference rates; правила неполных данных — в разделе 10.

Показывать limit, fact, remaining, progress, состояние превышения. Превышение бюджета предупреждает, но не запрещает реальный расход.

Изменение базовой валюты профиля не изменяет currency/limit уже существующих бюджетов и шаблонов. Кнопка «Повторять каждый месяц» создаёт шаблон; изменение шаблона влияет только на ещё не материализованные будущие периоды.

## 6. Атомарность, параллельные запросы и повтор команды

Для этого персонального приложения допустимо сериализовать изменения одного workspace: это проще и надёжнее, чем начинать с оптимизации параллельных проводок.

Каждая мутация финансовых данных, настроек, категорий и связей выполняется в DB::transaction:

1. Первым действием взять user_settings текущего user через SELECT ... FOR UPDATE.
2. Проверить command_key и request_hash для финансовой команды, включая POST/PATCH/отмену.
3. Прочитать актуальные записи, проверить revision и права.
4. При необходимости заблокировать затронутые accounts в стабильном порядке ID, затем связанные entities.
5. Рассчитать результат на актуальных данных; проверить все правила.
6. Записать всё, включая audit и command result; увеличить workspace_revision.
7. Commit. Обновление клиентского кэша и внешние эффекты — после commit.

Все пути записи, включая админ-команды, JSON restore, команды CLI и тестовые фабрики, меняющие существующий workspace, должны соблюдать этот протокол. Обновление last_seen_at не является финансовой мутацией.

Нельзя открыть транзакцию, прочитать старый balance, а затем взять lock: под InnoDB можно получить старый снимок. Проверку проводить после блокировки, с корректной стратегией чтения выбранной СУБД. Не полагаться на отключённую кнопку или обычную read-then-write проверку.

Idempotency-Key: UUID команды, сохраняется в UI до получения определённого результата. При сетевой ошибке повторяется тот же key.

- Одинаковый key + одинаковый payload возвращает прежний результат.
- Исключение после полного restore: key прошлого поколения отвечает WORKSPACE_REPLACED, как описано в разделе 11.3.
- Одинаковый key + другой payload → 409 IDEMPOTENCY_CONFLICT.
- Успешная финансовая команда никогда не повторяет эффект из-за timeout/retry.
- Revision mismatch → 409 STALE_REVISION; пользователю предлагается обновить данные, не перезаписывать изменения другого окна.
- Deadlock можно ограниченно повторить целиком; внешние API и отправку писем не выполнять внутри повторяемого финансового transaction closure.

Проверка конкурентного списания: из остатка 1000 две параллельные команды по 800 должны дать один успех и один отказ, итог 200. Проверять реальными отдельными соединениями production-типа СУБД.

Отчёт/dashboard возвращает согласованный снимок с workspace_revision. В одном ответе остатки, цели и связанные суммы должны соответствовать одной версии данных.

Для остановленного шаблона удаление месячного budget не должно автоматически восстанавливать его при следующем ensure. В модели месяца предусмотреть явную отмену лимита, например disabled boolean: API DELETE помечает месячный override как disabled, а ensure уважает его.

History счёта использует GET /operations?account_id=... и включает обе стороны transfer/exchange без дублирования одной операции.

Фильтры журнала: account_id, type, category_id, goal_id, liability_id, date_from/date_to, status, текст description. Определить стабильную сортировку occurred_on DESC, created_at DESC, id DESC. Все списки пагинируются; не загружать весь workspace при каждом открытии страницы.

Новые category/goal/liability endpoints должны отличать запрет физического удаления из-за истории от сетевой ошибки. Действие архив/отмена доступно пользователю вместо необъяснимого FK failure.

### 7.2. Формат запросов и ответов

Пример exchange:

~~~json
{
  "type": "exchange",
  "from_account_id": "<source-account-uuid>",
  "to_account_id": "<target-account-uuid>",
  "amount_minor": "180000",
  "target_amount_minor": "10000",
  "occurred_on": "2026-10-02",
  "description": "Обмен в накопления"
}
~~~

Currencies и effective_rate выводятся сервером из счетов и сумм. Если клиент передаёт валюты как подтверждение формы, они должны точно совпасть. При quoted-rate режиме присылается quoted_rate, а target может рассчитываться сервером.

Пример command response:

~~~json
{
  "data": {
    "operation": {
      "id": "<operation-uuid>",
      "type": "exchange",
      "status": "posted",
      "amount_minor": "180000",
      "currency_code": "MDL",
      "target_amount_minor": "10000",
      "target_currency_code": "USD",
      "effective_rate": "18.000000000000",
      "revision": 1
    },
    "affected_balances": [
      {"account_id": "<source-account-uuid>", "currency_code": "MDL", "balance_minor": "20000"},
      {"account_id": "<target-account-uuid>", "currency_code": "USD", "balance_minor": "10000"}
    ]
  },
  "meta": {"workspace_revision": 42, "replayed": false}
}
~~~

affected goal/liability projections можно возвращать в той же data. Query cache после успеха обновляется ответом и/или инвалидируется по связям. Не добавлять amount к старому cached balance вручную.

Для PATCH/void/составных действий требовать expected_revision соответствующего агрегата. Для backup/apply — expected_workspace_revision из preview.

Единый формат ошибок:

~~~json
{
  "error": {
    "code": "INSUFFICIENT_FUNDS",
    "message": "После изменения на счёте недостаточно средств",
    "fields": {},
    "details": {
      "account_id": "<owned-account-uuid>",
      "currency_code": "MDL",
      "would_be_balance_minor": "-90000"
    }
  }
}
~~~

422 — неверная форма/валюта/сумма; 409 — недостаточность средств после изменения, конфликт revision, повторное погашение, конфликт команды; 401 — нет сессии; 403 — нет роли/подтверждения; 404 — чужой или отсутствующий финансовый объект. UI локализует по code и показывает field errors.

Ошибки не должны содержать SQL, секреты или сведения о чужих счетах. При неизвестном результате network timeout UI сохраняет command key и предлагает проверить/повторить запрос с тем же ключом.

## 8. Экраны и UX

### 8.1. Принципы

Главный сценарий: открыть с телефона и быстро записать расход. Mobile-first layout, удобный ввод суммы, крупные действия, краткие формы. На desktop — sidebar, широкие таблицы, фильтры и графики рядом.

На мобильном bottom navigation: «Главная», «Операции», центральное «+», «Счета», «Ещё». В «Ещё» — Цели, Бюджеты, Долги, Отчёты, Настройки. Цели доступны также из dashboard и savings accounts.

Существующие пожелания Finpay можно использовать как визуальный ориентир, если reference/assets доступны агенту. Конкретный UI kit не является зависимостью реализации и не требует копировать чужие иллюстрации. Пока отдельный дизайн не утверждён, сделать нейтральный согласованный интерфейс.

Для каждого экрана: loading, empty, error, retry и успешный результат. Нет заглушек под видом работающих функций. Формы не закрываются при ошибке API и сохраняют введённые значения.

### 8.2. Главная

Не называть income − expense «балансом».

| Показатель | Определение |
|---|---|
| Остатки на счетах / «Всего на счетах» | Сумма balances выбранных include_in_total счетов, отдельно по валютам |
| «Доступно» | Остатки regular accounts, с явным тем же правилом отбора счетов |
| «Отложено» | Остатки savings accounts; не прибавлять progress целей повторно |
| «Доходы за месяц» | Posted income в месяце, по валютам |
| «Расходы за месяц» | Posted expense в месяце, по валютам |
| «Денежный поток» | Доходы − расходы за месяц; переводов и opening balance нет |

Archived account с include_in_total=true продолжает участвовать в капитале; указать это в настройке. Сумма денег на выбранных счетах не называется «чистым капиталом», поскольку обязательства учитываются отдельно.

В этапе A не складывать 100 EUR + 100 USD как 200 единиц одной валюты. Показывать блоки по валютам. Base currency выбирает первый блок по умолчанию, но остальные не скрываются.

Savings rate считать только в понятном валютном контексте; при income=0 отображать «нет данных», а не Infinity/произвольный 0%. Не считать перевод в savings новым доходом.

Dashboard также показывает последние операции всех типов, ближайшие долги, основные цели и статус бюджетов. Выбранный месяц относится к cash flow; текущие остатки не меняются при смене месяца, и подписи это объясняют.

### 8.3. Журнал и формы

Журнал содержит все четыре типа; переводы отображаются как «откуда → куда», обмен — с обеими суммами. Категория, дата, описание, цель/погашение видны в деталях.

Форма расхода/дохода: amount, account, category, date, description. При отсутствии account предложить создание. Quick-add категории возвращает пользователя в ту же форму с выбранной новой категорией.

Форма transfer/exchange: source, destination, available source balance, суммы/курс, date, description. Нельзя выбрать одинаковый account. После смены счетов сбросить/пересчитать несовместимый курс, не переносить старую валюту скрыто.

Перед отменой показать действие и оба счёта перевода. Пользовательское действие может называться «Удалить запись» с пояснением, что её денежный эффект будет отменён; сервер сохраняет историю.

### 8.4. Счета

Единый список regular и savings, фильтры типа и архива. Каждая карточка: name, currency, balance, включение в итог. В деталях — история, transfer, income/expense и разрешённые настройки.

Ни один созданный regular account не пропадает из управления. Savings с целью показывает ссылку на неё; default/main account создаётся один раз, без дублей после повторного входа.

### 8.5. Цели, бюджеты, долги

- Цель: текущие деньги, потраченное, накопленный прогресс, target/deadline, account, статус и контекстные действия.
- Бюджет: month selector, category, currency, limit/fact/remaining, предупреждение о других валютах и превышении.
- Долг: три направления с понятными словами, counterparty, сумма/валюта, срок, open/settled/cancelled, отдельная кнопка полного погашения и история связанной операции.

При создании/отмене этих объектов форма ясно объясняет, будет ли движение денег. Это пользовательское значение действия, не техническая информация о backend.

### 8.6. Отчёты

Сохранить 6-месячное сравнение income/expense, структуру расходов, top categories и печать. Добавить явные period и currency filters.

График остатков считается из opening balances и операций по каждому account, включая transfer/exchange, в исходных валютах. Остаток на конец даты = opening balance + эффекты posted-операций с occurred_on <= date.

Старые opening balances не имеют даты возникновения: историческая линия является реконструкцией по записанным операциям, с этим начальным остатком, а не подтверждённой банковской выпиской. Не подставлять доход вместо opening balance ради графика.

Net flow и линия остатков — разные отчёты. Для целевых расходов и погашений доступны признаки/фильтры; суммы основного cash flow сохраняют семантику исходного приложения.

Печать отчёта включает выбранные period/currency, дату формирования и предупреждение о неполной конвертации, если она есть. Элементы управления и bottom navigation в печать не входят.

### 8.7. Настройки и admin

Профиль, язык, timezone, theme, base currency; категории; JSON backup/restore; управление офлайн-копией.

RO/RU/EN для всех системных подписей, ошибок и состояний. Пользовательские названия/описания не переводятся. Тема синхронизируется с профилем; локальная копия нужна, чтобы применить её до загрузки приложения.

Admin отделён маршрутом и проверкой роли. Сохранить users/retention/premium, last seen, список, поиск, изменение разрешённых полей. Формулу retention документировать: например, доля зарегистрированных пользователей с last_seen за последние 30 дней.

Управление правами/billing логируется. Финансовых сумм, операций и backup чужих users в admin нет. Удаление пользователя из admin не добавлять: аудит обнаружил лишь пустой handler.

## 9. Авторизация, безопасность и PWA

### 9.1. Web auth и профиль

Использовать Sanctum SPA session auth: Secure/HttpOnly session cookie, CSRF, корректные stateful domains и SameSite. Не хранить bearer/session secrets в localStorage.

Новая регистрация создаёт user/settings/system categories/default regular account одной согласованной серверной процедурой. Инициализация идемпотентна. Неподтверждённому пользователю показывается экран подтверждения.

Reset password включает письмо, экран ввода нового пароля, обработку истёкшей ссылки и завершение; отправить письмо без экрана завершения недостаточно.

Изменение email не сразу заменяет подтверждённый адрес: новый адрес pending до подтверждения. Привилегии нельзя менять через профиль, backup или mass assignment.

### 9.2. Вывод и защита

- User strings выводить как обычный текст средствами React; не использовать innerHTML/dangerouslySetInnerHTML для description/name/comment.
- URL avatar разрешать только безопасных протоколов и валидировать на сервере; произвольный HTML не поддерживается.
- Авторизация и владение проверяются на каждом финансовом endpoint, а не только в списке.
- Rate limits на auth/reset, upload/preview и дорогие report endpoints.
- Финансовые JSON-ответы — Cache-Control: no-store; данные не попадают в публичный HTTP/CDN cache.
- Логи технические: не записывать passwords, tokens, полные backup и подробности всех пользовательских операций.
- Размеры upload, длины строк и количество импортируемых сущностей ограничены. SQL parameter binding; никаких SQL из файла.

### 9.3. PWA и офлайн

Manifest: название, короткое название, start_url, standalone, цвета, обычные и maskable icons. HTTPS. Корректный viewport, safe areas, работа клавиатуры, back navigation и перезагрузка вложенного route.

Service worker кэширует только versioned static assets и app shell. /api, /auth, /sanctum, backup и admin — network only. При обновлении показывать предложение перезапуска; не перезагружать незавершённую форму автоматически.

Офлайн-запись и background sync не реализовывать в этапе A. При отсутствии сети финансовые mutations недоступны; draft формы может жить в памяти до восстановления соединения, но не считаться сохранённой операцией.

Ограниченный офлайн-просмотр:

- По умолчанию хранится только app shell. Пользователь может включить «Сохранять последнюю сводку на этом устройстве».
- Для включённого режима сохранить один минимальный dashboard snapshot в IndexedDB, отдельный namespace user_id, revision и timestamp.
- Не кэшировать полный backup, admin, все комментарии и весь журнал. Не выдавать офлайн-снимок за подтверждённые текущие остатки.
- Офлайн-экран показывает время копии и запрет записи. После подключения выполнить свежую загрузку.
- Выход/смена аккаунта удаляют in-memory query cache и финансовые IndexedDB данные. Закрытые пользовательские экраны не должны показываться через browser back.
- Выход без сети дополнительно фиксирует pending logout; при восстановлении сети завершить серверный logout до автоматического восстановления сессии.
- Офлайн-копия не обещает защиту биометрией/шифрованием, которой нет в реализации.

Будущая совместимость с Capacitor: API client и domain logic отделены от browser UI, базовый URL конфигурируется. Native auth/storage/notifications подключаются через отдельный адаптер на будущем этапе, а не через токены в localStorage сейчас.

## 10. Новые функции этапа B

### 10.1. Справочные курсы и мультивалютная аналитика

Отделить:

1. Фактический курс конкретного exchange — выводится из реально списанных/полученных сумм.
2. Reference rate для оценки отчётов — внешний справочник, не изменяет деньги и операции.

Первый provider — BNM, официальный экспорт курсов к MDL. Endpoint и XML-схему проверить по действующей официальной странице, не полагаться на устаревший URL из примеров. Provider interface допускает замену источника.

fx_reference_rates:

- id, provider;
- currency_code, effective_on;
- mdl_per_unit decimal;
- published nominal/value и provenance для диагностики;
- fetched_at, version.

Нормализовать опубликованное значение на одну единицу валюты: mdl_per_unit = published_value / nominal. Для MDL значение всегда 1. Проверять currency/date/nominal > 0/value > 0 и полноту ответа; XML не должен разрешать внешние сущности.

~~~text
amount_in_T =
  amount_in_S * mdl_per_unit(S, date) / mdl_per_unit(T, date)

пример условных справочных курсов:
1 EUR = 20 MDL
1 USD = 18 MDL
100 USD ≈ 90 EUR
~~~

Эти цифры — тестовые fixtures, не курс на дату документа.

Два режима оценки:

- Monthly cash flow / budgets: для каждой операции reference rates на её occurred_on.
- Текущий общий остаток / savings: reference rates на выбранную дату оценки, по умолчанию «сегодня».

Не использовать текущий курс для всего исторического cash flow. Не использовать effective_rate одного личного exchange как универсальный курс всех операций.

При отсутствии курса на день можно использовать последний опубликованный курс с effective_on <= requested date, максимум 7 календарных дней назад. Фактическую дату курса и факт fallback возвращать в meta. Будущий курс не применяется задним числом.

Если допустимого курса нет:

- операция в исходной валюте сохраняется и доступна;
- сумма не считается нулевой и не исчезает из отчёта;
- consolidated report возвращает incomplete=true, отсутствующие пары/даты, известную часть суммы и исходные неконвертированные суммы;
- UI не подписывает известную часть как полный итог; показывает «нет полного расчёта» и суммы по валютам;
- запись операции не блокируется из-за внешнего provider.

Валютная конвертация округляет каждую оцениваемую operation до minor unit валюты отчёта, затем суммирует. Budget fact использует тот же алгоритм. Reference rate records/version включать в техническую метаинформацию отчёта и cache key; base currency и период также входят в ключ.

Изменение base currency пересчитывает представление. Original amount, currency, balances, goal target и фиксированный budget limit не меняются.

Reference fetch выполняется сервером с timeout и кэшем. Не ждать BNM внутри транзакции сохранения финансовой операции. Периодическое обновление допускается через cron хостинга; ручная загрузка истории идемпотентна.

При коррекции опубликованного rate сохранять версию/источник вместо незаметной перезаписи уже использованной записи. Индикативные пересчитанные отчёты могут обновиться с новой версией; первичная история денег не обновляется.

В этапе B добавить endpoints GET /fx/reference, POST /operations/quote и параметры display_currency для dashboard/reports. Quote не резервирует деньги и не гарантирует банковский курс.

### 10.2. CSV import/export

Новый сценарий, не часть старой миграции.

Минимальный собственный CSV формат для экспорта полного журнала:

~~~text
operation_id,type,date,account_id,account_name,amount,currency,category_code,category_name,description,from_account_id,from_account_name,to_account_id,to_account_name,target_amount,target_currency,effective_rate,status,goal_id,liability_id
~~~

Правильное CSV quoting, UTF-8, экранирование переносов/кавычек. Суммы в основных единицах с десятичной точкой. Предусмотреть безопасный режим просмотра в Excel, который защищает пользовательские текстовые поля от formula injection; собственный importer должен понимать этот режим, чтобы не портить round trip.

В импорте банковского CSV первой версии поддержать только income/expense:

1. Загрузка и обнаружение delimiter/encoding с явным подтверждением.
2. Mapping date/amount/direction/currency/description/category.
3. Выбор account для строк; currency должна совпадать со счётом.
4. Preview нормализованных строк, ошибок и возможных дублей.
5. Применение только выбранных валидных строк одним batch command.

Если банковский CSV содержит две стороны перевода, не пытаться незаметно объявить их income/expense или автоматически склеить. Пользователь исключает строки и заводит перевод отдельно. Собственный versioned CSV с обеими суммами может импортировать transfer/exchange при наличии однозначных account mappings.

goals/liabilities в CSV — контекст, не источник восстановления связанных сущностей. Если их нет в целевом workspace, не восстанавливать связи по имени; использовать JSON backup для полного восстановления или отклонить такую связанную строку с объяснением.

Дубли:

- ID собственного экспорта и уникальный bank transaction ID — строгие признаки при наличии.
- Hash account/date/amount/currency/нормализованного описания — только возможный дубль.
- Две реальные одинаковые покупки не сливаются автоматически.
- Preview позволяет включить подозрительные строки явно.
- batch key и source row keys предотвращают повторное применение одного и того же upload.

Начальные лимиты: 5 MiB и 10 000 строк. Валидация и mapping выполняются до финансового commit. Apply добавляет данные, не удаляет текущий workspace, проверяет итоговые balances и полностью откатывается при ошибке.

Endpoints: GET /operations/export.csv; POST /csv/preview; POST /csv/apply. JSON restore и CSV import имеют разные UI и semantics.

## 11. JSON backup и атомарный restore

### 11.1. Новый формат

~~~json
{
  "schema": "norocel.workspace",
  "version": 2,
  "exported_at": "2026-10-02T10:00:00Z",
  "settings": {
    "locale": "ru",
    "base_currency_code": "MDL",
    "theme": "system",
    "timezone": "Europe/Chisinau"
  },
  "accounts": [],
  "categories": [],
  "operations": [],
  "operation_revisions": [],
  "goals": [],
  "budgets": [],
  "budget_templates": [],
  "liabilities": [],
  "liability_settlements": []
}
~~~

Экспорт — согласованный снимок одного workspace. Суммы представлены строками минимальных единиц. Сохраняются voided operations, разрешённые legacy markers, архивы и финансовая история изменений.

Не экспортировать password hashes, сессии, tokens, роли, admin/billing flags, служебные idempotency records и чужую идентичность. При restore все user_id/actor attribution нормализуются к текущему владельцу; restore не может дать права или подключить чужие строки.

Пользовательские профильные настройки можно восстановить; подтверждённый email, пароль и права пользователя не менять.

### 11.2. Preview

Проверка файла ничего не удаляет и не записывает в рабочие финансовые таблицы.

Проверить:

- schema/version, размер, количество объектов;
- типы, точность/пределы сумм, UUID, уникальность ID;
- все FK и отсутствие чужих/неразрешённых ссылок;
- account currency, формы операций, валидность transfer/exchange;
- соответствие goal account/currency;
- семантику settlement: тип, сумма, валюта, account, posted status;
- бюджетные category/type/period/currency;
- итоговые остатки и согласованность вычисленных состояний.

Начальные ограничения JSON: 10 MiB, максимум 50 000 operations, суммарно 100 000 объектов. Это конфигурация; при необходимости её расширить после проверки памяти и времени выполнения хостинга. Не заявлять поддержку файлов больше лимитов.

Preview возвращает статистику, warnings/blockers, прогноз остатков по account/currency, список legacy исключений, hash файла и token проверки.

Новый versioned формат проверяется строго: неизвестные поля и попытки восстановить credentials/privileges отклоняются. Legacy adapter может исключить известные старые admin/billing/email fields из пользовательского backup, но обязательно сообщает об этом в warnings.

Preview token связан с user, file hash, нормализованными данными, expected_workspace_revision и expiry, например 30 минут. Клиент не может заменить проверенный payload перед apply.

### 11.3. Apply

Restore — полная замена пользовательских финансовых данных, а не merge. До подтверждения интерфейс перечисляет реальные области замены: счета, категории, операции, цели, бюджеты, долги и их связи.

1. Убедиться, что preview не истёк и workspace не изменился.
2. Создать доступную пользователю резервную копию текущего состояния; её получение не заменяет atomic rollback.
3. Взять общий workspace lock.
4. Повторно проверить revision, hash, структуру и обязательные инварианты.
5. В одной DB-транзакции заменить данные в FK-безопасном порядке.
6. Проверить итоговые balances и количества записей.
7. Увеличить workspace_revision, commit, вернуть согласованную сводку.

Если хотя бы одна вставка/проверка падает, прежний workspace целиком остаётся рабочим. Не использовать параллельные HTTP DELETE и последовательные INSERT из React.

Больше 50 000 операций не импортировать частями с промежуточным commit под видом атомарного restore. При будущем увеличении объёма возможен staging workspace с атомарной сменой поколения.

Служебные dedup records существующих команд не удаляются при restore. Команды предыдущего поколения workspace должны сохранять tombstone и отвечать 409 WORKSPACE_REPLACED, если их повторяют после замены; они не должны создать старую операцию заново. Добавить workspace generation к user_settings и command records для этого случая.

Legacy JSON адаптер описан далее. Не применять unversioned файл напрямую как новый формат.

## 12. Перенос из текущего Norocel / Supabase

### 12.1. Подготовка и источники

1. Прочитать AGENTS.md и правила репозитория. Проверить реальный commit, migrations и существующий export/import код.
2. Зафиксировать исходный commit и контрольные суммы экспорта. Аудит описывает 25d3a31; если код изменился, перечислить изменения.
3. Снять полную схему и read-only серверный экспорт данных, если такой доступ разрешён и предоставлен. Альтернативный источник для одного пользователя — его старый JSON backup.
4. Разделить экспорт финансовых данных и Auth identity. Пользовательский JSON не является достоверным источником ролей и подтверждённого email.
5. Все преобразования сначала выполнить в dry run и на отдельной базе. Не менять исходные данные.

Старый JSON не versioned; profile использует snake_case, остальные entities — camelCase. Реальную структуру ключей и обязательных полей извлечь из кода, реализовать отдельный LegacyNorocelAdapter и fixtures настоящего формата. Не писать importer по приблизительным названиям из этого ТЗ.

### 12.2. Mapping данных

| Источник | Цель и правило |
|---|---|
| auth.users + profiles | users/settings по явному ID map; подтверждённый email берётся из Auth |
| accounts | Сохранить name, regular/savings, currency, opening balance, include flag и ID |
| income/expense transactions | Одна posted operation, те же суммы/даты/account; category → FK |
| transfer/exchange transactions | Одна operation, оба счёта, обе суммы, обе валюты; не разделять на income/expense |
| Default categories в i18n.js | Реальные системные category rows с прежними system codes |
| Custom categories | Сохранить ID/имя/тип; old key хранить в mapping |
| goals | Сохранить target/currency/deadline/account; проверить старые saved/status и computed progress |
| budgets.monthly_limit | Текущий месячный budget + repeat template; currency фиксируется из профиля на момент экспорта |
| liabilities | Сохранить principal/type/counterparty/date/comment; создать settlement link только при доказанном соответствии |
| profiles.language/currency | locale/base currency; не менять валюты старых счетов |
| local theme | При индивидуальном переносе по желанию загрузить локальное значение, иначе system |

Decimal values читать из исходного JSON/SQL как точные десятичные числа, а не предварительно парсить через JS Number. Преобразование в minor units должно быть точным. Лишние нулевые знаки допустимы; ненулевая точность сверх scale — blocker до явно согласованного правила округления.

Особые случаи:

- Old exchange_rate не соответствует двум фактическим суммам: деньги сохраняются; effective_rate рассчитывается из сумм; старый курс сохраняется в legacy_metadata и выводится в отчёте миграции. Не менять target amount под старый неверный курс.
- Неверный старый type transfer/exchange при корректных счетах/суммах можно нормализовать по валютам; original type сохранить в legacy_metadata, изменение перечислить.
- Счёт менял валюту, и история не соответствует его текущей currency: blocker. Не конвертировать историю или переименовывать валюту незаметно.
- Удалённая custom category оставила raw key: создать явно архивную migrated category правильного income/expense типа с этим ключом в provenance. Не заменять всё на «Прочее».
- Одинаковый old key для income/expense разрешать по паре (kind, key), а не по key без типа.
- Goal без account: сохранить legacy saved amount/status в совместимом read-only отображении. Не создавать новый счёт с таким остатком автоматически — это могло бы добавить уже учтённые деньги. Связывание требует отдельного решения.
- Goal с stored spent и валидным связанным expense: если завершение было ручным, перенести completion marker в соответствующую операцию. Если это невозможно доказать, сохранить legacy_status и сообщить об исключении.
- Старый settled debt с отсутствующей/неподходящей operation: blocker до выбора владельца. Не создавать повторное погашение.
- Неразрешённые account/goal/category/settlement ссылки не пропускать незаметно.

Исторические бюджетные планы и их валюты восстановить точно невозможно: в старой схеме нет периода/валюты. Сохранить известный текущий лимит и правило повторения; для прошлых месяцев показывать «план не восстановлен», если его достоверно нет. Не выдавать текущий лимит за подтверждённый план каждого прошлого месяца.

### 12.3. Перенос авторизации

Предпочтительный первый способ — создать Laravel identities с прежними UUID/явным mapping и организовать установку нового пароля через reset flow.

- Не просить пароли пользователей и не пытаться получить их из browser storage.
- Совместимость существующих password hashes проверять отдельно, если перенос хэшей действительно выбран; не предполагать её.
- Email verification flag/роли/billing брать только из доверенного серверного источника.
- Если имеется лишь пользовательский backup, импортировать его в уже авторизованный Laravel account; не восстанавливать чужой Auth identity из файла.
- Supabase sessions не превращать в Laravel sessions. После переключения пользователь входит заново.
- Не создавать второй main account при первом входе импортированного user.

Для репетиции использовать fake/local mail transport. Рассылка реальным пользователям при переключении — часть отдельно согласованного запуска, не автоматический результат dry run.

### 12.4. Обязательная сверка

Отчёт миграции для каждого user:

1. Количество accounts, transactions/operations по каждому type, categories, goals, budgets и liabilities.
2. Остаток каждого account по старой формуле и по новой, точная delta в minor units.
3. Обе стороны каждого перевода/обмена, даты, суммы и account mappings.
4. Income/expense месячных итогов в исходных валютах, без reference-rate конвертации.
5. saved_now / spent_on_goal / funded_lifetime каждой цели и отмеченные изменения lifecycle.
6. Открытые и погашенные obligations и соответствие settlement.
7. Архивные placeholders, legacy markers, нормализованные types/rates, budget assumptions.
8. Неразрешённые blockers. Их список не может быть пустым только потому, что строки пропущены.

Критерий автоматической успешной сверки: для каждого account delta=0, суммы/валюты/даты операций сохранены, все ссылки валидны. Ожидаемые отличия отображения и нормализация метаданных перечислены отдельно.

### 12.5. Репетиция и переключение

- Запуск миграции имеет source fingerprint / run ID и не дублирует данные при повторе.
- Сначала импорт на чистую тестовую базу и проверки из раздела 14.
- Проверить UI тем же набором данных и контрольными сценариями.
- Подготовить краткий runbook с backup, dry-run command, import command, сверкой, переключением frontend/API и входом пользователей.
- Перед финальным экспортом рабочие записи останавливаются на уровне источника, а не только скрытием кнопки в старом UI.
- После финального переноса повторить сверку, затем переключить приложение. Старый Supabase оставить read-only на период проверки.

Rollback: до первых записей в новой версии можно вернуть старую. После новых записей нельзя просто переключиться на старую базу: сначала нужен отдельный перенос новых операций или явное решение владельца. Этот предел должен быть записан в runbook.

Исходную Supabase-базу и старые exports не удалять в ходе этого задания.

Этап B:

- Cross-rate USD→EUR и нормализация nominal отличного от 1.
- Historical cash flow использует rate на date каждой операции.
- Missing reference rate → incomplete с исходными суммами, не ноль.
- Новая base currency не меняет original amounts и цели/бюджеты.
- Повтор CSV batch не создаёт дубли; одинаковые реальные покупки можно сохранить обе.
- CSV с quoting/newlines и опасными формулами безопасно экспортируется/читается.
- Ошибка CSV apply откатывает весь batch и не трогает старые данные.

### 14.2. Интеграция и UI QA

Backend tests запускать на production-типе СУБД. Concurrent cases — отдельные соединения/процессы; один connection и rollback тестового framework не доказывают безопасность гонок.

Минимальный E2E:

1. Регистрация/подтверждение/вход → счёт → доход → расход.
2. Второй счёт → перевод → обмен → детали → edit/void.
3. Цель → пополнение → частичный целевой расход → завершение → отмена расхода.
4. Обязательство → погашение → отмена погашения.
5. Бюджет → расход → превышение → другой месяц.
6. Export → preview → restore; отдельно ошибочный import.
7. Logout → другой user: никаких предыдущих данных.

Проверить вручную или доступным browser automation:

- мобильный viewport примерно 360–390 px, tablet и desktop;
- клавиатуру при вводе суммы, safe areas, sticky/bottom nav, доступность основных кнопок;
- light/dark/system, RO/RU/EN, длинные пользовательские названия;
- refresh вложенного route, browser back, истёкшую сессию, network timeout;
- PWA install и обновление версии;
- offline shell / opt-in snapshot / запрет записи / очистку после logout;
- печать отчёта.

Если физический iPhone/Android недоступен, указать ограничение. Проверка viewport в Chromium не называется проверкой Safari iOS.

### 14.3. Условия готовности A

- Все обязательные функции из 1.1 доступны через UI и реальный API.
- Нет скрытых transfer/exchange и недоступных regular accounts.
- Все money fields точные; перечисленные сценарии целостности и доступа проходят.
- Goal spend, settlement и restore не могут оставлять половину изменений.
- Concurrent/retry/edit/void не нарушают остатки и связи.
- Отчёты различают balances и cash flow, не суммируют разные валюты.
- JSON restore безопасен и обратим атомарно при ошибке.
- Пароль действительно сбрасывается до нового входа.
- Сборка, typecheck, необходимые tests и UI QA завершены с честным отчётом.
- Миграция воспроизводима; реальные данные либо сверены, либо отсутствие их проверки явно указано.
- Развёртывание на выбранном хостинге описано и проверено в тестовой среде; production cutover не выполнен без отдельного согласованного запуска.

## 15. Источники и принятые решения

1. NOROCEL_AUDIT.md, 02.10.2026: текущая функциональность, формулы остатков/целей, shape переводов, проблемы целостности и формат legacy backup. Это источник текущего поведения, не подтверждение live данных.
2. [Laravel Sanctum — SPA authentication](https://laravel.com/framework/docs/13.x/sanctum#spa-authentication): браузерная сессия и CSRF; native auth будет отдельным адаптером.
3. [Laravel — database transactions](https://laravel.com/framework/docs/13.x/database#database-transactions): транзакционная граница команд.
4. [Laravel — pessimistic locking](https://laravel.com/framework/docs/13.x/queries#pessimistic-locking): механизмы блокировок; конкретный workspace protocol выбран этим ТЗ.
5. [BNM — официальные курсы и XML export](https://www.bnm.md/ro/content/ratele-de-schimb): потенциальный provider этапа B; его endpoint/schema агент проверяет при реализации.

Решения этого ТЗ: React PWA + Laravel, один operations row на перевод, opening balance как фиксированное поле, неотрицательный текущий остаток, прогресс цели по saved + spent, полное погашение обязательства, этап A с суммами по валютам, новые reference rates/CSV в этапе B.

Изменения против старой реализации перечислены явно: FK/архив категорий, архив счетов, полный журнал, атомарные команды, отказ от destructive client import, защита конкурентных/повторных записей, versioned backup, конкретные месяц/валюта бюджета, полный password recovery. Финансовые суммы не меняются ради этих исправлений.
